# CI Gating: Automated Dependency-Tree Discovery — Design

**Status:** design, not yet implemented. Supersedes `docs/superpowers/plans/2026-08-10-larql-cli-wasm-and-safe-gating.md` as the forward-looking source of truth for this effort. That plan doc is not deleted or wrong — it's the historical record of the R&D that produced the 20-pattern taxonomy this spec builds on, and it stays as reference. But its actual applied source-level edits (the hand-placed `cfg`/`forbid` annotations currently on this branch) are not treated as a durable foundation by this spec — see §4.

## 1. Purpose

Three days of hand-driven `wasm32v1-none`/`forbid(unsafe_code)` gating by an LLM coding agent covered 10 of 13 crates and never reached the root (`larql-cli`). The actual value produced by that effort is the **20-pattern taxonomy** — the catalogued knowledge of what breaks and why. The actual hand-applied annotations are not a durable asset; most of that code is not being kept. This spec exists to replace hand-driven gating with a **cheaply, mechanically re-runnable automated discovery tool** that can regenerate the gating boundary layer by layer, leaf by leaf, root by root, against whatever the codebase looks like at the time — including after a rebase.

Where a crate's native/portable split already aligns with module or file boundaries, **physical crate extraction (§7) is the preferred realization of that boundary**, not inline `#[cfg]` gating — real, working precedent exists in this repo's own history (§3), and inline `#[cfg]` remains the correct tool only for the finer, sub-function granularity extraction can't reach (§8, pattern 21).

## 2. Scope and the decidability boundary

The campaign targets exactly two properties, deliberately, not as an arbitrary starting pair:

- **Does this crate compile under `wasm32v1-none`?**
- **Does this crate contain unsafe code?**

Both are fully decidable by the compiler — a binary verdict, zero ambiguity, no separate analysis tool required. This is why `wasm32v1-none` specifically (not `wasm32-unknown-unknown`) is the near-term target: `wasm32v1-none`'s minimal runtime (no host imports, no OS, no dynamic capabilities) means that **compiling to it at all already entails the containment properties** a richer target's analysis would need a separate pass to verify — import-freedom, bounded/deterministic behavior are implied by what the target is even capable of, not approximated by the compile signal. `wasm32-unknown-unknown` reintroduces those richer-runtime questions and is explicitly future scope, revisited when it becomes relevant, not solved preemptively.

**Explicitly and permanently out of scope for this mechanism**: call-graph containment analysis, mutation-tested Datalog rule sets, binary `.wasm`-level certification. Not because they're uninteresting — a materially larger, more formally rigorous prior attempt at exactly this existed (§3) — but because building and maintaining that class of tool is a different, harder engineering problem than "run the compiler and act on its verdict," and pursuing it here repeats the specific failure mode that killed the prior attempt (§3). This project is not automating for all possible properties — only the ones the compiler itself decides.

## 3. Relationship to prior art

Two genuinely distinct prior efforts exist in this repo's history, both abandoned, neither an ancestor of the current work. Both are **reference material, not authoritative** — specifically because both predate understanding that's now been established (forbid-as-decidable-oracle; `wasm32v1-none`-compile-implies-containment):

- `crates/larql-compute/docs/adr/005-safe-buffer-reads.md` (2026-04-06) — predates blanket forbid by four months, proposes consolidating FFI unsafe into one audited function rather than forbidding it. Superseded: the codebase and the understanding of forbid-as-oracle have both moved on; this ADR does not carve out a standing exception for `larql-compute`/`larql-compute-metal`. Whether those crates need any accommodation gets discovered the same way as every other crate — real, fresh `forbid` attempts against current source, not inherited from a four-month-old document.
- A much larger, more formally rigorous, fully-abandoned wasm32 campaign on sibling branches (`origin/wasm/wasm32v1-none-gating`, `origin/claude/wasm-blocker4-source-gates`, 162–185 commits deep) — full-workspace source-cfg gating, a Datalog-based (`ascent` crate) call-graph certifier (`cargo xtask wasm-certify`) with a mutation-testing zero-survivor gate, a binary-level `.wasm` certifier (`larql-wasm-certify --strict`, checking import/indirect-call/`memory.grow`/recursion freedom via `wasmparser`), and a formal ADR classifying every LQL `Statement` variant by certification status. **It was abandoned because, by the time it neared completion, the codebase had drifted several weeks behind `chrishayuk/larql`'s ongoing architectural changes, forcing a full rebase-and-redo.** This is the direct cautionary precedent for §4: a large, slow, manually-maintained effort against a continuously-moving upstream target goes stale before it finishes, regardless of how rigorous the underlying analysis is. Confirmed by direct source inspection: neither the Datalog analyzer nor the binary certifier ever touched Rust source-level AST editing — both are pure `wasmparser`-on-compiled-bytes analysis. Nothing from them is salvageable for the auto-remediation mechanism in §7, which (per §7's own revision) turns out not to need custom diagnostic-parsing scaffolding at all — `cargo dylint --fix`/`cargo fix` already provide it.

**A third, independent lineage exists — real, working, physical crate extraction, not source-cfg gating — and unlike the two efforts above, it does not predate current understanding; it is orthogonal to it (a different axis: code topology, not the forbid-vs-deny question) and is weighted accordingly, not filed as reference-only.** Confirmed by direct query against every ref in this repo, not memory: two extraction lineages exist, on branches distinct from either abandoned campaign above —
  - `larql-lql` → `larql-lql-core` (birth commits `3c25be2c`/`e8be883b`, "Tier-0 parser crate, wasm32v1-none safe"), present today at the tip of four branches (`origin/refactor/wasm-lql-core-split`, `origin/feat/plan4-agent`, `origin/feat/query-driven-extractors`, `origin/impl/plan1-foundation`).
  - `larql-vindex` → `larql-vindex-wasi` (birth commits `d20c7003`/`239b1682`, "reduce src/ to wasm32-wasip1-compilable surface"), present today at the tip of two branches (`origin/wasm/vindex-wasm32uu`, `origin/wasm/wasmi-host`).

  Both extracted crates are still physically present, unmodified, at every one of those six branch tips — never reverted, only never merged forward into a shared main. This is real, working precedent for the extraction mechanism in §7, not a hypothesis.

## 4. Rebase/upstream-resilience (first-class, standing requirement — not a one-time recovery step)

`origin/main` (the fork's own main branch) is stale and is being replaced by this branch, not merged into — confirmed empirically: `upstream/main` is 426 commits ahead of `origin/main`. But `upstream/main` is *also* 24 commits ahead of this branch's own fork point, while this branch carries 99 commits of gating work upstream doesn't have — a genuine three-way divergence, not simply "behind a stale fork main."

The general requirement is not specific to this one 24-commit gap: **the CI must survive arbitrary future upstream edits as a standing property, continuously — not as a special "post-rebase recovery" operation run once.** The next upstream sync will produce a different, unpredictable diff; whatever this session's specific check found is evidence the mechanism needs to actually work, not the thing the design targets.

Two complementary properties, not one:

1. **Discovery runs as a standing part of the CI, not a special recovery mode.** If a crate arrives with no gating annotations — a new crate pulled in from upstream, or an existing one rewritten heavily enough that its gating no longer applies — the same mechanism that gates the rest of the tree (§5, §7) picks it up automatically on the next relevant run. Rebase survival is one instance of this standing property, not a distinct case requiring its own handling.
2. **Preserve gating for free wherever git's own three-way merge says clean; rediscover wherever it says conflict, or wherever gating annotations are simply absent.** This uses only tools already given and already decidable — git's merge outcome is a well-defined, already-existing binary signal, not something new to build or classify. No attempt is made to distinguish *why* a merge conflicted (rename vs. rewrite vs. anything else) — that's exactly the open-ended classification problem this project does not take on. A conflict, or a crate/region with no gating annotations at all, is simply the trigger for running discovery (§5, §7) on that spot; a clean merge needs no tool involvement at all.

**Empirical evidence the fragility is real, and precisely located** — checked via `git merge-tree` (non-destructive trial merge, no working-tree changes, no commits) against `upstream/main`'s 24 newer commits: **5 real conflicts** among 26 files touched by both sides, including a **modify/delete conflict** — `crates/larql-cli/src/commands/primary/shannon_cmd.rs` was deleted entirely by upstream's architectural work while this branch's gating work (this session included) had modified it, making that gating work moot. The other 21 overlapping files, including `crates/larql-cli/src/main.rs` and `.github/workflows/quality.yml`, merged cleanly with no help needed — property 2 above, already working for free wherever changes don't textually collide. `larql-cli-gating.yml` doesn't exist upstream at all, so it can't conflict; it carries straight through regardless.

The fragility is entirely in **hand-placed, per-file source annotations** — exactly the class of artifact this spec already treats as disposable by default (§1), with property 2 above as the refinement: a clean git merge preserves them for free with no tool involvement; a conflict (or an absent annotation) is simply where discovery re-runs, not a case requiring the tool to explain why the merge conflicted. This is the direct fix for the failure mode that killed the prior campaign (§3): the tool must never require multiple days to converge, or the same staleness trap recurs.

## 5. Forbid-unsafe-tree mechanism

- **`forbid`, never `deny`, anywhere, no exceptions.** Where a `deny`-with-local-`allow` pattern would be needed to make something compile alongside a `forbid` elsewhere, the `deny` gets removed — not weighed case by case. This is fixed policy, not a per-instance tradeoff.
- **Root-parameterized.** Today `larql-cli`; the mechanism must generalize to any future root (binary or library) without redesign — matching the retired `clippy-fix.yml`'s own `ROOTS = [...]` precedent.
- **Attempted crate-root first, on every crate in the root's transitive closure, unconditionally.** Never assume a crate needs narrowing because a different crate did, or because an old document/ADR says so. Narrowing to module, then per-*item* (the finest unit Rust's attribute system supports — there is no finer addressable scope for lint control) happens **only after a fresh, real CI run proves it's structurally forced**, and the fix is recorded via §6, not inherited from precedent.
- **Leaves-first sequencing**, matching the existing `wasm32v1-none-ubuntu → {others, metal} → cli-ubuntu → cli-others → forbid-unsafe` tiering. This decomposes the spec along the dependency tree itself: each tier is the same mechanism (attempt forbid, narrow only where the compiler forces it, record via §6) applied to the crates at that depth, gated on the tier below it succeeding — not a separate spec per crate, one mechanism applied uniformly per tier.
- **Demonstrated end-to-end this session**, not theorized: a crate-root `forbid` probe on `larql-cli`, dispatched via a real CI run (bypassing the `wasm32v1-none` chain, which was blocked on an unrelated finding), produced exactly 38 genuine `E0453` conflicts across 22 files that call `ndarray::s!` (a macro whose internal `#[allow(unsafe_code)]` cannot coexist with an enclosing `forbid` — confirmed live, not inherited from the original claim's narrative), plus 2 plain forbidden-unsafe-block errors with no macro involvement at all, in two files (`walk_cmd.rs`, `trajectory_trace_cmd.rs`) that had been **incorrectly** grouped under the `ndarray::s!` exemption. Fixed and validated: restoring `forbid` to those two files produces exactly the expected 2 errors and 0 new `E0453`s, confirmed via a second live CI run.

## 6. Structured exemption registry

Every `forbid` exemption gets a machine-readable record with a reason-code drawn from a fixed vocabulary (e.g. `macro-hidden-unsafe:ndarray::s!`, `ffi-required`) — never a free-text comment. This makes every exemption mechanically checkable against what the compiler actually says, closing exactly the class of bug found and fixed in §5: a comment claiming a reason (`ndarray::s!`) that neither grep nor the compiler's own output supported for two of the seven files it covered.

**Two clippy restriction lints mechanically enforce exactly what this registry needs — confirmed by a real run against this repo's own two genuinely-exempted files, not assumed.** `cargo clippy -p larql-cli --no-deps -- -W clippy::undocumented_unsafe_blocks -W clippy::multiple_unsafe_ops_per_block` (both lints are off by default, so never seen by a plain `clippy` run): both fire on exactly the 2 already-known real unsafe blocks from §5's pattern-18 finding, and nowhere else — `walk_cmd.rs:10` (2 unsafe operations, `std::mem::zeroed()` + `libc::getrusage()`, bundled in one block) trips both lints; `trajectory_trace_cmd.rs:707` (1 operation, `std::slice::from_raw_parts`) trips only `undocumented_unsafe_blocks`. Zero new surface found — exactly the already-mapped set, not an open-ended one. Neither lint carries a `MachineApplicable` suggestion (confirmed from the actual output: `help:` text only, no suggested diff) — not a gap, the correct boundary: writing the real safety rationale, or deciding how to re-split a multi-op block, needs the one-time human/LLM judgment call §7's opening line already carves out ("recognizing a genuinely new diagnostic shape the first time"), applied here to exactly 2 already-located files, not an ongoing loop. Both belong in `[workspace.lints.clippy]` — Cargo's own inherited-lints mechanism, confirmed already in use in this repo at crate scope (`larql-compute-metal/Cargo.toml`'s `[lints.rust]`), just not yet promoted to workspace scope — not a custom per-crate flag or an xtask wrapper: the same "existing tool, not reimplemented" test as everything else in this spec.

## 7. Auto-remediation

Not a custom-built tool — the design test throughout this section is: determinism implies an algorithm; an algorithm implies a tool; a tool that already exists gets called, not re-architected. LLM/agent involvement is warranted at exactly one point below (recognizing a genuinely new diagnostic shape the first time), never in an ongoing per-instance or per-run loop.

**`cargo clippy --fix`** handles rustc/clippy's own native `MachineApplicable` suggestion tier — unchanged, not reimplemented.

**`cargo dylint --fix`** handles the residue clippy's own `--fix` doesn't resolve, for anything shaped as a Rust-source fix. Confirmed by direct source inspection, not assumed: `cargo dylint --fix` literally shells out to `cargo fix` (`dylint_internal::fix()` → `cargo("fix")`, and `cargo-dylint`'s own test suite proves a third-party lint's `MachineApplicable` suggestion gets applied end-to-end through this path). That means the entire "apply a fix, recompile, iterate to a fixed point" mechanism is inherited for free from cargo's own established, ecosystem-wide-battle-tested machinery — no custom outer loop, no custom dispatch runtime. It also means the *application* itself is safe by construction: cargo-fix applies suggestions via precise byte-range splicing at the compiler's own reported span, not by reparsing and reprinting the file — the same mechanism responsible for every other machine-applicable fix in the Rust ecosystem, not something this project needs its own CST-editing library to reproduce.

**Dylint's actual boundary — confirmed against rustc's own compilation pipeline, not asserted.** `rustc_interface::passes::analysis()` calls `sess.dcx().has_errors_excluding_lint_errors()` → `raise_fatal()` *immediately after type-checking, before `rustc_lint::check_crate()` runs* — the exact entry point every `LateLintPass` (dylint's and clippy's shared mechanism) hooks into. Any `E0425`/`E0432`/`E0463`-class hard error anywhere in the crate aborts compilation before that lint pass executes at all — structurally, not as an engineering gap to work around. Separately, `dead_code` itself is implemented directly in the compiler (`rustc_passes::dead`), not as a pluggable `LintPass`, so a dylint lint cannot attach a suggestion to rustc's own existing `dead_code` diagnostic — a project-specific lint has to independently detect the same condition and emit its own diagnostic with a `MachineApplicable` suggestion (zero-width insertion via `span.shrink_to_lo()`/`shrink_to_hi()`, the standard idiom for "add this attribute line above this item" — confirmed: 76 real usages of exactly this pattern in `rust-lang/rust`'s own source). Writing that lint is genuine work, done once, using rustc's own established lint-authoring API — but built and run end-to-end this session (real `LateLintPass`, real `span_lint_and_sugg`, real green CI applying a real `cargo dylint --fix`), which surfaced a further, non-obvious constraint: **no idempotency check is possible at the HIR level**, because `#[cfg]` attributes are stripped during macro expansion before HIR (and therefore before any `LateLintPass`) ever sees them — confirmed directly, the prototype lint re-fired on its own freshly-applied fix in the same run. A production version needs a source-text or early-AST check for "is this item already gated," not a HIR-level one.

**Cargo.toml-shaped fixes are a different class entirely — dylint operates on Rust source via rustc's compilation model and cannot touch Cargo.toml.** Patterns 1/6/9/12/7/10 (dependency `std`-feature splits, transitive/sibling feature-unification) need a small, separate script using **`toml_edit`** — confirmed format-preserving directly from the crate's own description ("parse and modify toml documents, while preserving comments, spaces and relative order of items"), unlike the plain `toml` crate, which round-trips through a data structure and loses exactly that. The diagnosis step for these (which dependency actually needs the split) is `cargo tree -i <suspect>` — an existing, deterministic command, not something requiring interpretation.

**A third class exists that dylint structurally cannot reach and no existing tool answers — named honestly, not papered over.** Confirmed empirically this session: reverting `larql-factory`'s hand-applied gates back to never-gated and running a fresh `wasm32v1-none` check produced 96 real compile errors, zero `dead_code` — and roughly 75 of those 96 were exactly the kind dylint's own pipeline-position constraint (above) rules it out of: `std`/`String`/`Vec`/`ToString` unavailable under `no_std`, in files that had simply never had `use crate::prelude::*;` added because they'd never been compiled for this target before. rustc's own self-fix for `E0425` is never `MachineApplicable` for this shape either — resolution only ever suggests candidates that already resolve in the current, post-`cfg` scope, and a cfg'd-out identifier has no such candidate. Whether a given file needs the prelude import, or the whole item needs gating instead, is project-specific policy no compiler pass encodes — exactly what the original hand-gating commit (`89249ae2`) decided manually, case by case. This needs bespoke, pre-typeck, cfg-aware tooling that does not exist yet anywhere in the ecosystem checked — an honest gap in this design, not one to assume away.

**Crate extraction — preferred over inline `#[cfg]` at module/file granularity; inline `#[cfg]` (including pattern 21's expression-level technique, §8) stays correct only below that granularity, where extraction can't reach.** The question of whether a mature, formally-correct decomposition tool exists that could skip inline cfg-gating entirely resolves like this: the *decision* of where the boundary falls is already fully decidable by the same oracle this section already trusts completely — `cargo build`/`check` against the target — applied as an iterative subtractive/pruning loop rather than a single-shot static analysis: attempt the build of the would-be-portable subset, prune whatever fails, repeat until clean. This is not a new technique to invent: it is exactly how `larql-vindex-wasi` (§3) was actually built, and it is sound by construction for the same reason inline-`#[cfg]` discovery already is — every kept item is proven by a real compile success, every pruned item is proven necessary to prune by a real compile failure, no guessing at any step.

What is genuinely not yet mature is the *mechanical execution* once the boundary is known: moving files, rewriting the manifest, fixing the rare visibility/orphan-rule snag (the `larql-factory` worked example needed exactly one — `Recipe::from_yaml` becoming a free function). No single packaged tool does this end-to-end — checked directly: `rust-analyzer`'s extraction assists stop at within-crate module boundaries; the one tool that attempts cross-crate extraction (`cargo-crate-split`) is unadopted (1 star, ~3 months old) and syn-based with acknowledged blind spots (misses glob re-exports and type-inferred calls). The individual primitives it would be built from are already mature and already used elsewhere in this section — `cargo new` + `toml_edit` for manifest/workspace wiring, plain `git mv` for files that need zero modification (the actual shape of both real precedents in §3 — clean, unmodified moves preserve semantics by construction, not by review). This gap is the same honest, named kind as the third class above: real, not papered over, but bounded and small, not a blocker to starting.

**Priority is not a guess — it comes from a real cross-reference of this branch's dependency graph (`cargo metadata`) against its per-crate source classification, both built this session:**
- **First-wave (best evidence, lowest blast radius):** `larql-factory` (in-degree 1 — only `larql-cli` depends on it; exactly 3 named native entry points — `build::run`, `card::render`, `estimate::*` — everything else already portable) and `larql-lql` (in-degree 1; the crate's own `lib.rs` doc states its native/portable split was arrived at via "a full-crate survey," i.e. confirmed complete, not provisional; only 8/71 files touch a wasm32 cfg at all).
- **Second-wave, after the mechanism is proven on the first wave:** `larql-core` (well-bounded, but fan-in 4), then `larql-models`/`larql-compute` (clearly bounded whole-module splits, but fan-in 7/6 — highest leverage *and* highest blast radius, so not first).
- **Not yet:** `larql-vindex`/`larql-inference`/`larql-kv` — pervasive per-file mixing (118/319, 77/214, 78/142 files respectively), no clean module boundary to extract along, and — not incidentally — the exact crate profile (35–55% of files cfg-touched) matching this repo's own documented `clippy --fix` incident (`wasm32-clippy-fix.yml`'s birth commit `6b6dcf4c`: a local `--fix` run "silently deleted or narrowed several imports/bindings that were 'unused' only from wasm32v1-none's perspective, but load-bearing on native," undetected because only the wasm32 leg was checked afterward) — the automated risk concentrates exactly where the structural data already says it does.
- **Never a fit:** `larql-compute-metal`/`larql-router-protocol` are wholesale-native (`target_os`/`cfg`-excluded at the module-declaration level already — nothing portable to pull out); `larql-cli` has no `lib.rs` target and is permanently native by design (its own doc: "expected to remain permanently native, its whole point is CLI file/network/GPU I/O").

**Scope discovery for extraction must come from `cargo metadata`, never a hand-maintained crate list** — not a preference, a lesson this exact CI already paid for once: commit `55bee251` ("pattern 8: sibling-path-dependency-not-yet-gated") exists specifically because three transitive dependencies were missing from a hand-copied crate list; the retired `clippy-fix.yml`'s `discover` job fixed this by deriving scope from real `cargo metadata` dependency-graph data. Any extraction tool that skips this inherits the identical surprise-discovery failure mode.

**Extraction tooling lives inside the gating pipeline (`larql-cli-gating.yml`), never as a parallel workflow requiring manual sync** — the other lesson this CI already paid for: `clippy-fix.yml`'s own five-commit arc (standalone workflow → generalize → largest-rewrite → retire-and-fold-in, the fold-in itself landed a commit late because of a `git add` staging accident) is the concrete cost of building automation as a second system instead of extending the first. The `xtask`-shaped orchestrators from the abandoned campaign (§3) are useful precisely as a shape reference here — a thin sequencer calling existing tools in a fixed order (`cargo metadata` → `cargo check`-driven prune loop → `git mv`/`cargo new`/`toml_edit` → a real CI build of both resulting crates) — never as license to re-architect a custom policy engine, which is exactly the design this project rejected earlier in favor of `cargo dylint --fix`.

**Boundary stability is not yet settled — gate the first extraction on a live check, not on this analysis alone.** No stretch of green `wasm32v1-none-*` runs exists yet on the current 7-job graph (job structure itself only reached its current shape today); the one fully-completed run was red by design ("errors are the deliverable"). Consistent with this project's standing rule against pre-gating ahead of a real result: extracting `larql-factory`/`larql-lql` gets staged behind a live `gh api` check that their current `wasm32v1-none-*` legs are actually green first, not assumed green from this document.

**No off-the-shelf tool does the whole thing end-to-end — checked directly, not assumed.** No existing GitHub Action or crates.io package automates "determine and apply cfg gates for a Rust crate against a cross-compilation target" as one packaged whole. The pieces (`cargo fix`, `dylint`, `toml_edit`, `cargo tree`) are each established and existing; wiring them together for this project's specific target/policy combination is the one part that's genuinely bespoke, and it should be as thin as possible — a CI step invoking each existing tool in sequence, not an application with its own control-flow architecture. §4's preservation mechanism doesn't depend on any of this tooling either — it's git's own merge outcome, a separate concern.

Changed files upload as the literal changed files (via `git diff --name-only` fed into `actions/upload-artifact`'s `path:` input, preserving directory structure), never a patch requiring `git apply` — already built and validated in `wasm32v1-none-ubuntu`'s existing auto-fix step this session.

## 8. Fix-mechanism map

Not a curated body of pattern-knowledge an agent interprets at runtime — each entry names which *existing* mechanism (§7) a taxonomy pattern maps to. Seeded from the full 20-pattern taxonomy in `plan.md`, filtered by the same determinism test: **if the action for a matched diagnostic isn't identical every time, it isn't decidable enough to map to a fixed mechanism.**

**Maps to a dylint lint** (source-code fix, deterministic once written): 3 (whole-module native exclusion), 11's dead-code rule (this repo's own standing default — `#[cfg(not(target_arch = "wasm32"))]` at the exact flagged span, never deletion without in-place evidence), 14 (private-hasher-leaks — widen visibility + add a re-export), 16 (cross-target alias inference — insert the one explicit type annotation), 18's actual fix mechanism (the per-item `forbid` exemption at the exact span `E0453` names, recorded via §6).

**Patterns 3 and 11 route to crate extraction first, not the dylint lint, wherever the containing crate is in §7's first- or second-wave tier** (`larql-factory`, `larql-lql`, then `larql-core`/`larql-models`/`larql-compute`) — the dylint fix (inline `#[cfg]` at the flagged span) stays the mechanism for every other crate, and for anything below module granularity inside a first/second-wave crate that extraction itself doesn't reach.

**New pattern 21, confirmed this session, not theorized: expression-level `#[cfg]` inside the call that actually needs it, rather than gating the containing function.** Rust supports `#[cfg(...)]` directly on individual array/tuple/call-argument elements — validated empirically, not assumed: for a function assembling several outputs where exactly one element depends on something native (the shape pattern 11's dead-code rule produces when applied naively at function granularity), applying `#[cfg(not(target_arch = "wasm32"))]` to that one element compiles clean on stable rustc, with zero behavior change to the function's portable callers and no new function/wrapper needed. Confirmed head-to-head against the alternative (splitting the function into a portable core plus a native wrapper): both compile clean, but the split alternative silently changes the function's native-observable behavior and requires relocating a test — the inline element-level `#[cfg]` is strictly the smaller, safer fix wherever the diagnostic's shape allows it (the native dependency is confined to one expression already sitting inside an array/tuple/call-argument position).

**Maps to the `toml_edit` + `cargo tree` script** (Cargo.toml fix): patterns 1/6/9/12 (dependency `std`-feature splits), 7/10 (transitive/sibling feature-unification).

**Not fix rules at all — already expressed as CI architecture, not entries here**: patterns 8 (leaves-first sequencing — §5), 15 (native oracle must run alongside the wasm32 oracle — §11), 17 (fmt-check blind spot), 19/20 (coverage-baseline handling, tiered CI topology). These are structural lessons about how the CI itself must be built, not diagnostic-to-edit mappings.

**Excluded, decisively, not ambiguously**: pattern 13 (nominally-distinct cross-crate hashmap types). This is not a hard case within the taxonomy — it isn't a member of it. It's a downstream symptom of one specific implementation choice made while hand-fixing pattern 4 (each crate independently reinventing its own portable hasher/collections module, producing structurally-identical but nominally-distinct types across crate boundaries) — not a property of the codebase's actual `wasm32v1-none`/unsafe classification. The correct response is not a mechanical rule for the symptom; it's not repeating the implementation mistake that caused it — §7's eventual portable-collections handling (wherever pattern 4's fix is needed) should use a single shared implementation rather than independent per-crate reinvention, so this class of problem doesn't recur in the first place.

## 9. Inventory

The deliverable is not "CI green/red" — it's a queryable map. Per item: `wasm32v1-none` compilability (schema extensible to the future multi-target lattice — `wasm32-unknown-unknown`, `wasip1`, `wasip3`, emscripten, wali-linux-musl — added when each becomes relevant, per §2) crossed against unsafe-code presence, built from the compiler's own exhaustive diagnostic output rather than scraped from human-authored comments.

**Cross-referenced against real data**: `metavacua/larql-to-sparql`'s GitHub issues (167 total, 162 open), joined on the existing `crate:<name>` label taxonomy that already matches this campaign's crate structure exactly (`crate:larql-vindex`: 47 issues, `crate:larql-cli`: 45, `crate:larql-lql`: 23, `crate:larql-models`: 21, ...), further joined against the repo's own `evidenced:problem`/`speculative:solution` epistemics labels. This makes "how much of the problem surface concentrates in expensive, non-portable, unsafe code vs. safe portable code" a directly answerable query against real data, not a hypothesis.

## 10. CI architecture (implemented and live-validated this session)

- **Dual trigger, deduped correctly.** `push` (survives the oracle going dark if a PR closes without merging — confirmed this actually happened) plus `pull_request`, deduped via a concurrency group keyed on the actual head commit SHA (`github.event.pull_request.head.sha || github.sha`), not `github.ref` (which differs between the two event types for the identical commit). Verified live: an initial oversight let both trigger types run to completion simultaneously for the same commit (~60 redundant jobs); the SHA-keyed fix was confirmed via a subsequent push, where the second-arriving trigger correctly cancelled the first within seconds.
- **`clippy-fix.yml` retired.** Its separate `discover` job, deps/roots two-tier split, and patch-plus-standalone-verify-native-job ceremony are replaced by folding the fix-and-upload mechanism (§7, once built) directly into the relevant tier's existing job — no separate crate-discovery duplication, no patch/`git apply` indirection.
- **Per-crate matrix legs exist for feature-combination coverage, not lint-visibility scoping — verified, not assumed.** Cargo's `--cap-lints` (`compute_cap_lints`, gated on path-source `is_local()`, not on which package is named via `-p`) means every crate in this all-path-dependency workspace already compiles uncapped whether built directly or pulled in as a dependency of the root — confirmed against this repo's own `larql-lql.yml`, which explicitly needs `--no-deps` precisely because a dependency's lint debt *does* surface without it. The real reason to matrix per-crate is Cargo's feature-unification, not lint suppression: a confirmed concrete instance — `larql-core`'s `msgpack` default feature is requested by zero crates in `larql-cli`'s actual dependency closure, so it's exercised only by `larql-core`'s own direct leg; a root-only build would never touch that code path at all.
- **Cross-crate, root-rooted reachability ("is this item ever actually called starting from `larql-cli`, across crate boundaries") is a different question from per-crate `dead_code`, and genuinely lacks mature source-level tooling upstream** (open rustc issue rust-lang/rust#120079; clippy #5828 closed as out of scope; the accepted-but-unshipped `-Z dead-fn-elimination` compiler proposal). This is not a gap to fill here: the `wasm32v1-none` linker already computes true, monomorphized, cross-crate reachability as a side effect of producing the compiled binary. An optional, non-gating observability step — `twiggy garbage` against the linked `larql-cli` wasm artifact — can surface this for free, post-link, with no separate analysis tool; it stays informational, never a gate, since the linker is already the authoritative arbiter of what's actually in the binary. What per-crate `dead_code` + narrow `#[cfg]` (§7, §8) already provides isn't a weaker version of this — it's the different, still-necessary question of whether a crate's own compilation unit contains code unreachable within itself.

## 11. What "red" means — pinned per axis, not re-litigated per finding

Stated explicitly because the failure mode has recurred: an agent (this session included, once) treating an expected, deliverable "red" as a defect to route around, or vice versa, at inconsistent points.

- `wasm32v1-none` red-until-gated: **expected and correct.** The failure to compile is the discovery signal driving the next fix-mechanism-map entry (§8), not a bug in the CI.
- `forbid-unsafe` red-until-narrowed-or-genuinely-caught: **expected and correct.** A real, uncaught unsafe block or macro conflict is the deliverable, exactly as demonstrated in §5.
- Auto-fix (§7) still red after uploading a partial fix: **informational, not itself a failure.** The upload captures whatever progress was made regardless of final pass/fail; the re-run clippy check afterward is the real, honest gate.
- `deny(unsafe_code)` appearing anywhere, for any reason: **always wrong**, per §5 — never a case-by-case call.
